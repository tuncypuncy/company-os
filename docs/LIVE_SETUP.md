# Live foundation setup

The live PostgreSQL and Supabase Storage adapters are implemented. They have not been connected to an external project: no credentials or project identity were available. Demo data is isolated and must never be copied into the live database.

1. Configure server-only `APP_MODE=live`, an exact HTTPS `APP_ORIGIN`, and `DATABASE_URL` securely. Use a direct or session-mode PostgreSQL connection suitable for server-side `pg`. Certificate verification is mandatory; connection-string TLS overrides are removed. Supply `DATABASE_CA_FILE` with a trusted provider certificate if the system trust store does not suffice. Never disable verification.
2. Run `npm run db:migrate` once as a deployment step with the application stopped. Use a migration-capable database account. Runtime access must be server-only; do not expose the `company_os` schema through public Data API configuration. Database grants, backups and restore testing need deployment-specific review.
3. Set `BOOTSTRAP_EMAIL`, `BOOTSTRAP_PASSWORD` (14–256 characters), `BOOTSTRAP_NAME`, and `BOOTSTRAP_ROLE=OWNER` securely, then run `npm run user:create`. Remove these bootstrap values afterwards. Repeat with `OPERATIONS_MANAGER` to provision an operations account. Passwords are scrypt-hashed; eight-hour sessions are stored as token hashes. No email is sent. Self-service password reset and MFA are not implemented.
4. Create a **private** Supabase Storage bucket named `company-os-invoices`, with a 10 MB limit and PDF/PNG/JPEG MIME restrictions. Set `PRIVATE_STORAGE_PROVIDER=supabase`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_STORAGE_BUCKET`. The service key stays server-side and must not use a `NEXT_PUBLIC_` variable. Restrict network egress to the actual project hostname after its identity is known. Bucket privacy is checked before uploads, downloads and cleanup. Do not change a private bucket to public. The application creates no buckets automatically.
5. Alternatively, use `PRIVATE_STORAGE_PROVIDER=local`, a persistent private `PRIVATE_FILES_DIR`, and `DURABLE_STORAGE_CONFIRMED=true`. Ephemeral hosting disk does not qualify. Existing local attachments stay local after a provider change; preserve their original volume. Each attachment records its provider/bucket so changing the configured default cannot redirect old objects.
6. Run `npm run live:check`, then build and start. This verifies the database migration, active real owner, HTTPS origin and private bucket configuration. It does not perform a storage write or establish commerce readiness. Verify a real login and a reviewed invoice upload/download with authorized test evidence before production use.

Upload rollback removes the stored object when database posting fails. A failed cleanup logs a credentials-free reconciliation notice; storage and database writes are not a distributed transaction. A periodic orphan reconciliation job is still required. Storage SDK contract tests use fictional responses and do not prove live Supabase access.

No Shopify, Meta or CJ sync is connected. Financial balances, tax rules, store/entity mapping and filing dates still require confirmed source records.
